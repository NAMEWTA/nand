## 方案目的

将“浏览器自动化与多 AI 工作台”调研作为 NAND 的产品方案评审输入，讨论如何在内置浏览器中实现统一提问、多站回答采集、结果对比，以及后续可控的网页助手能力。

本 Issue 包含完整调研报告，面向产品经理和研发评审，不包含实现代码。这里的阶段规划与验收条件是产品建议，具体范围、技术选型和排期仍需结合 NAND 的宿主环境验证。

## 核心建议

- **先交付多 AI 官网协同工作台**：用户在真实官网登录，选择参与站点，统一输入问题，查看逐站进度，保存和比较回答。
- **参考现有 Multi AI Workspace 的业务能力**：发送前检查、分阶段提交、站点适配、回答完整性校验、会话历史和提示词快照。
- **参考 ORCA GitHub 项目的浏览器集成**：稳定的页面身份、页面与账号配置管理、同页人工接管、每页操作队列，以及页面关闭或进程变化后的控制会话恢复。ORCA 分析依据为官方源码，不以技能说明作为实现证据。
- **按能力选取开源组件**：确定步骤优先参考 Playwright / Puppeteer；代理工具接口参考 agent-browser / Playwright MCP；自然语言多步任务参考 Browser Use / Stagehand；视觉定位可参考 Midscene 作为补充。
- **把可靠性做成可见的产品能力**：区分“已提交”“待确认”“生成中”“采集不完整”“保存失败”，支持按站恢复，避免故障后整组重发。

## 建议的用户流程

1. 新建任务，选择 AI 站点和账号环境。
2. 登录并确认页面就绪，在统一输入框编辑问题与提示词。
3. 检查所有目标，向本轮选中的站点发送。
4. 在真实网页中观察回答，必要时暂停并人工接管。
5. 在统一结果视图中比较回答、追问、重新采集和导出。
6. 通过任务历史恢复上下文，并能定位每条回答对应的问题、站点和官网会话。

## 建议推进顺序

| 阶段 | 主要交付 | 评审或验证重点 |
| --- | --- | --- |
| 概念验证 | 三类代表性站点的登录、连续三轮发送、长回答采集、重启恢复 | 验证 NAND 宿主中的页面控制、账号保持与兼容性 |
| 第一阶段 | 多 AI 工作台、逐站状态、原文保存、人工恢复 | 完成真实登录条件下的发送与采集闭环 |
| 第二阶段 | 持久任务、异常恢复、重新采集、历史迁移、适配诊断 | 不静默串会话或重复发送 |
| 后续阶段 | 指定页面的网页助手、可复用流程、外部助手接入 | 过程可观察、可停止、可验证结果 |

初版建议集中验证上述闭环；完整 Chromium 分支、任意网站自主代理和云端浏览器集群放到独立的后续决策中。

# 浏览器自动化与多 AI 工作台功能调研报告

调研日期：2026 年 10 月 8 日  
适用读者：产品经理、产品负责人及参与方案评审的研发负责人  
研究对象：Multi AI Workspace 插件、成熟浏览器自动化方案、ORCA 官方 GitHub 项目的内置浏览器  
内容范围：功能、实现原理的产品化解释、开源借鉴点、交互建议和实施路径。全文不包含代码或操作命令。

## 一 核心结论与决策建议

**这个插件本质上是一款多 AI 官网协同工作台。** 用户在一个地方组织问题，把同一份内容发送给选中的多个 AI 官网，在真实网页中观察生成过程，再把回答归档为可以回看、比较和导出的本地记录。它利用用户在浏览器中的网站登录状态，不要求用户为每个模型配置开发者 API Key。

**它已经包含一套针对 AI 聊天网站的自动化流程，但尚不是能执行任意网站任务的通用浏览器代理。** “给三个 AI 同时提问”与“让 AI 自己搜索、筛选商品、填写业务系统”是两种不同的产品能力。前者可以主要依靠确定的规则实现，后者通常需要额外的任务理解、规划、页面判断和结果验证能力。

**自研浏览器可以内置这些功能，通常不需要从零研发浏览器内核。** 对于以多 AI 工作台为起点的产品，更合理的路线是使用成熟浏览器引擎，掌握页面、账号和任务的管理权，再建设统一的控制层与站点适配层。选择完整 Chromium 分支，主要适用于“我要做用户日常使用的浏览器”这一更大的目标。

**ORCA 是非常有价值的集成参考。** 它已经把内置页面、浏览器控制、任务工作区、账号配置和代理工具接口连接起来。特别值得学习的是：人和代理操作同一页面；操作始终绑定确定的页面；每个页面有独立队列；页面销毁或切换进程后能够清理和恢复控制会话。它能减少底层浏览器集成工作，但不会自动提供多 AI 对比所需的回复采集和业务历史。

建议的产品组合是：

| 要解决的问题 | 优先借鉴对象 | 借鉴重点 |
| --- | --- | --- |
| 一次提问多个 AI 并保存结果 | 当前 Multi AI Workspace | 站点适配、发送前检查、分阶段发送、答案完整性、会话归档 |
| 在自己的应用里容纳并控制真实网页 | ORCA 与 Electron | 页面注册、同页接管、账号分区、页面级队列、故障恢复 |
| 稳定完成确定的网页步骤 | Playwright 或 Puppeteer | 元素定位、等待条件、输入与点击、网络与页面状态观测 |
| 向外部 AI 助手开放浏览器能力 | agent-browser 或 Playwright MCP | 简洁工具接口、页面快照、元素引用、结构化结果 |
| 执行自然语言描述的多步任务 | Browser Use 或 Stagehand | 观察、行动、验证的闭环，以及规则与 AI 的混合执行 |
| 处理难以通过网页结构定位的界面 | Midscene 等视觉方案 | 截图理解、视觉定位、结果检查，作为补充执行方式 |

以上是面向本项目的选型判断，不是统一性能排名。具体依据和边界在下文逐项展开。

## 三 当前插件具体实现了什么

### 3.1 用户可以完成的完整工作流程

以“请几个 AI 分别评审一个产品方案”为例：

1. 打开工作台，选择需要参与的 AI 站点。
2. 在各官网登录，保留官网自己的模型选择和功能设置。
3. 在统一输入框编辑问题，按需附加提示词模板。
4. 勾选本次接收问题的站点，点击发送。
5. 工作台先检查所有目标是否能接收消息，再写入内容并提交。
6. 用户在多个真实官网面板中观察各自的回答。
7. 插件判断回复是否结束，采集当前轮回答并保存。
8. 用户通过统一历史查看多家回答，复制或下载为 Markdown。
9. 后续追问继续使用各官网自己的上下文；新任务则建立新的本地任务并重建站点面板。

主要价值是减少重复输入、标签切换、复制整理和上下文管理的工作量。最终答案仍由各官网产生，插件负责组织操作和整理结果。

### 3.2 已实现的功能清单

| 功能 | 当前行为 | 产品价值与边界 |
| --- | --- | --- |
| 多官网并排展示 | 在扩展工作台内加载真实官网页面 | 保留官网原有聊天体验，不必自行重建每家聊天界面 |
| 八个预置站点 | DeepSeek、Kimi、Coze、ChatGPT、Claude、通义千问、MiniMax、豆包 | 站点列表有明确范围，不能理解为添加任意网址后即可自动操作 |
| 默认面板 | 新配置下默认打开 DeepSeek、豆包、通义千问 | 已保存的用户配置会覆盖默认设置 |
| 面板管理 | 打开、关闭、左右移动、刷新、最大化、恢复、调整宽度 | 便于关注某个回答，同时保留其他站点 |
| 两种布局 | 平铺与自适应布局 | 适应不同面板数量和屏幕尺寸 |
| 本次发送目标 | 从已打开的面板中独立选择，支持全选和清空 | 打开页面不等于每轮都必须向它发送 |
| 统一草稿 | 发送前草稿留在工作台 | 避免边写边污染多个官网输入框 |
| 提示词库 | 新增、编辑、删除、排序、多选模板，并预览组合结果 | 将角色要求、输出格式等复用到不同问题 |
| 提示词版本留存 | 每轮保存当时使用的模板内容与原问题 | 以后修改模板不会改变旧提问的记录 |
| 发送检查 | 判断登录、验证挑战、已有草稿、正在生成等状态 | 避免覆盖用户在官网上已写的内容 |
| 分阶段发送 | 只读检查、填写校验、最后提交 | 减少某些站点不可用时其他站点被提前发送的情况 |
| 单站状态反馈 | 加载、需要登录、就绪、提交中、已发送、错误等 | 能定位失败发生在哪个站点 |
| 回复采集 | 网络会话数据、官网复制能力、限定回答区域的页面内容等多种来源 | 避免只能复制当前屏幕中的一小段文字 |
| 统一历史 | 本地任务、提问轮次、各站发送状态和回答 | 把多家官网的结果归到同一个产品任务中 |
| 历史管理 | 搜索、重命名、置顶、删除、切换与详情查看 | 支持持续积累和复用结果 |
| 统一对话阅读 | 按提问轮次查看多个 AI 的回复，支持展开与定位 | 降低反复去原网站寻找答案的成本 |
| 内容导出 | 当前任务、单个 AI 会话、最近一轮等范围的复制或 Markdown 下载 | 将结果转入笔记和后续工作 |
| 历史迁移 | 导入和导出带版本的 .maiw.jsonl 文件 | 转移本地会话记录，不等于迁移网站账号 |
| 外部标签页模式 | 在普通浏览器标签页打开站点并保持控制绑定 | 为无法稳定嵌入的页面提供替代入口 |

### 3.3 不能误认为已经具备的能力

当前工作台没有建立“理解任意任务并自主执行”的通用代理循环。它不会根据一句“帮我订票”自动规划、跨站搜索、比较并提交订单。

它也没有实现统一附件上传、统一切换各官网模型、跨站深度思考开关同步、自动综合多家答案、结果投票评分或证据真伪核验。这些可以在产品上增加，但需要独立设计。用户仍可在官网原生界面中手动使用相应功能。

当前面板管理会避免同一服务商重复添加，因此“同一网站同时使用两个账号比较结果”不是现成能力。浏览器内的网站账号也不等于本地历史里的任务：前者决定登录身份，后者只负责整理工作记录。

本地记录并不是官网全部历史的镜像备份。部分采集策略可能读取到一个官网会话中的更多消息，但正常导出主要围绕工作台保存的任务、轮次和回答；不能承诺完整保存网站所有分支、附件和历史。

### 3.4 README 与实际实现存在的差异

| README 或概括性描述 | 当前源码显示的实际情况 | 应使用的产品表述 |
| --- | --- | --- |
| 默认打开 DeepSeek 与 Kimi | 默认面板是 DeepSeek、豆包、通义千问 | 默认组合以当前界面与状态配置为准 |
| 只操作 DOM，不调用站点内部接口 | 发送主要通过网页操作；回复采集包含网络观察、请求重放和部分同源会话接口读取 | 使用官网交互发送，并通过多种方式采集回答 |
| 仅保存最终回复纯文本 | 已保存 Markdown、采集来源、完成状态、修订与部分结构化消息证据 | 支持可追溯的本地回答归档 |
| 只展示官网，不自行渲染回答 | 实时面板是官网，统一历史详情会渲染保存的 Markdown | 官网实时展示与本地统一阅读并存 |
| 新任务在官网点击新建对话 | 当前主界面路径创建新本地任务、更新面板身份并回到各站默认地址；底层另有新建对话命令 | 新任务会重建工作上下文，仍需验证各站首页是否确实进入新对话 |

最后一项尤其需要产品验收：**本地出现“新任务”，不自动证明每个官网的上下文都已清空。** 当前主界面没有直接调用底层的新建会话消息路径，应验证各站实际导航后的状态。

这些差异说明项目正在演进。以当前源码作为功能清单依据，比直接引用 README 更准确。依据：[README](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/README.md)、[实际发送及新任务流程](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/entrypoints/workspace/workspace-app.tsx)、[网络采集入口](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/entrypoints/acquisition-network-main.content.ts)、[数据库记录](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/db/database.ts)。

## 四 插件实现原理的产品化解释

### 4.1 六个部分共同完成一次操作

| 部分 | 可以理解成什么 | 承担的工作 |
| --- | --- | --- |
| 工作台 | 用户的控制台 | 组织草稿、目标站点、面板、任务与历史 |
| 后台协调器 | 调度员 | 把一个动作发给正确的站点，汇总各站结果 |
| 页面桥接 | 驻留在官网里的执行员 | 接收操作请求，观察当前页面并回报状态 |
| 站点适配器 | 每家官网的操作说明 | 知道输入框、发送按钮、回答区域和完成信号在哪里 |
| 回复采集与质量检查 | 资料整理员 | 判断拿到的是不是当前问题的完整回答 |
| 本地数据库 | 工作档案 | 保存任务、提问、回答、来源和历史修订 |

扩展工作台不能像读取自己的页面一样直接读取所有跨域官网。它通过浏览器授予扩展的权限，让页面内的桥接逻辑工作，再由后台把消息送到对应面板。面板、浏览器标签、网页子框架和站点身份之间必须保持对应关系，才能避免把问题发错位置。

### 4.2 多站发送采用三个阶段

**第一阶段是只读检查。** 检查是否已登录、是否出现人工验证、输入框是否可用、官网是否已有未发送草稿、上一条是否仍在生成。此时不应改动官网输入框。

**第二阶段是填写与校验。** 把本轮内容写入各站输入框，读回确认一致，等待发送按钮可用。如果某站失败，对已经成功暂存的站点尝试撤回本轮内容。撤回时只清理仍与本轮内容一致的输入，避免删除用户随后手动修改的草稿。

**第三阶段才是提交。** 所有站点均准备好后，再向各站触发发送，并分别等待网页反馈。

这不是跨网站的严格事务。一旦部分网站已经接受发送，就不能保证把它们的消息撤销；在网络或页面变化时也可能出现“已点击但无法确认”的情况。因此，产品必须保留逐站结果，不应只显示一个整体“发送失败”，更不应默认重发所有网站。

源码中存在短时任务去重记录，但它不能等同于跨浏览器重启、跨网络故障的“绝对只发送一次”。依据：[后台协调](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/entrypoints/background.ts)、[站点基础策略](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/providers/base-dom-strategy.ts)、[任务去重记录](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/orchestration/task-ledger.ts)。

### 4.3 回复采集比发送更难

点击发送按钮往往只有一个动作；证明某段文字是“这个问题在这个会话里的最终完整答案”，需要同时解决多个问题：旧答案与新答案如何区分，是否还在生成，长对话有没有被网页隐藏，是否读到了错误分支，以及“正在思考”“复制成功”等状态文字有没有混入正文。

当前实现采用有优先顺序的采集方式：

1. **站点会话数据。** 对已适配的网站观察页面请求，并在受限范围内读取会话数据，校验消息关系、分页和分支。
2. **官网原生复制。** 利用目标回答自身的复制按钮取得文本，并验证是否属于当前回答；采集请求会尝试抑制对系统剪贴板的写入。
3. **限定区域的页面内容。** 前两种方式不能提供可信结果时，从当前回答区域提取内容并转换为适合归档的形式。

通过校验后选择一个来源作为结果，不把多个来源随意拼接成“完整回答”。否则可能出现重复段落、错位内容和无法证明来源的组合文本。

| 站点 | 已配置的优先采集思路 | 必须承认的边界 |
| --- | --- | --- |
| DeepSeek | 会话历史和消息父子关系 | 会话接口或数据结构变化后可能回退 |
| 豆包 | 会话消息链与分页 | 必须判断分页是否结束 |
| 通义千问 | 已观察到的会话数据与会话身份 | 数据结构存在不同形态，需持续维护 |
| Kimi | 消息列表、分页与消息链 | 需结合结束状态证明当前回答完成 |
| ChatGPT | 会话节点与当前分支 | 不能把其他分支的回答混进当前轮 |
| Claude | 会话消息、稳定身份及终态 | 同样依赖站点会话结构 |
| Coze、MiniMax | 原生复制优先，页面内容回退 | 当前没有上述六站对应的已验证接口采集适配 |

这里的“已配置”表示源码具备路径，不代表所有内部接口当日可用。网站内部接口不是公开稳定的第三方集成合同，其维护风险应单独列入产品成本。

依据：[采集策略引擎](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/acquisition/engine.ts)、[质量检查](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/acquisition/quality-gate.ts)、[原生复制](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/providers/native-copy.ts)、[采集版本设计](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/docs/changes/2026-09-01-provider-conversation-acquisition-v2/design.md)。

### 4.4 保存的是工作记录与证据

本地数据至少分为三层：一个任务包含多轮提问，每轮提问又包含多个站点的发送与回答记录。采集快照还记录来源、消息身份、完整性证据和修订，避免较晚到达的旧状态覆盖已经保存的最终结果。

用户看到的“完整会话导出”主要对应工作台记录的会话。当前历史迁移文件保存任务、轮次和各站回答，没有把整个采集快照表或完整提示词库作为独立数据集全部导出。因此不能把它宣传为“整个插件所有数据的完整备份”。

同样，切换历史主要恢复保存的官网地址和工作台布局。能否继续官网上的旧对话，还取决于该网站的对话是否存在、账号是否仍能访问。导入一份本地历史文件，不会在官网自动重建相同对话。

依据：[数据库](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/db/database.ts)、[历史迁移](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/db/history-transfer.ts)、[采集快照保存](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/db/acquisition-snapshot-service.ts)、[回复修订保护](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/messaging/response-revision.ts)。

### 4.5 内嵌官网是目前的结构性难点

插件把官网放进扩展页面的内嵌框架。为允许部分站点嵌入，当前实现会对指定工作台标签页中、预置站点的子框架响应移除防嵌入相关响应头，实际移除的包括完整内容安全策略响应头。

其范围是限定的，但代价不只是“多开几个页面”。站点登录策略、第三方存储限制、弹窗、验证码、页面防护和官网更新仍可能导致失败。修改响应头也不保证能解决所有问题。

因此，**自研浏览器最有价值的改善之一，是让每个 AI 官网作为受应用管理的独立浏览页面运行。** 从产品结构上减少对“把一个网站塞进另一个网页”的依赖。它不会解决全部登录与反自动化问题，却能去掉一大类嵌入限制。

依据：[嵌入策略](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/core/permissions/frame-policy-manager.ts)、[普通标签页接管](https://github.com/NAMEWTA/multi-ai-browser-extension/blob/b6b83ca90f0f67fbf25a676e7a8f6b8b34327800/src/entrypoints/background.ts)。

## 五 浏览器控制方法的全景

### 5.1 先区分不同层次

| 层次 | 解决的问题 | 典型方案 | 是否天然包含 AI |
| --- | --- | --- | --- |
| 浏览器容器 | 网页在哪里运行、如何显示、如何保存登录 | Chromium、Electron、CEF、WebView2 | 否 |
| 底层控制通道 | 外部程序怎样访问页面、输入、网络和截图 | CDP、WebDriver、WebDriver BiDi、扩展接口 | 否 |
| 自动化执行工具 | 怎样可靠定位、等待、点击和填写 | Playwright、Puppeteer、Selenium | 否 |
| 代理工具接口 | AI 助手怎样调用浏览器能力 | agent-browser、Playwright MCP、Chrome DevTools MCP | 提供工具，通常不替用户完成全部规划 |
| 智能任务执行 | 怎样把目标拆成步骤并根据页面变化调整 | Browser Use、Stagehand、Skyvern | 是，依赖配置的模型能力 |
| 产品业务层 | 如何管理任务、账号、结果、权限和恢复 | 当前插件、ORCA、BrowserOS 的相关设计 | 根据产品决定 |

这些方案经常叠加使用，不能把 MCP、Playwright 和 Electron 当成互相替代的同类产品。MCP 可以理解为 AI 助手连接工具的一种通用接口约定，本身不是浏览器内核，也不会自动解决网站兼容。

### 5.2 五种主要执行方式

**基于网页结构的操作。** 读取按钮、输入框、文本和页面层级，再操作确定的元素。速度较快，也容易检查结果；主要困难是网站改版、富文本输入框、虚拟列表和结构不规范的控件。

**基于浏览器调试协议的控制。** 通过浏览器本身提供的控制能力获取页面、网络、截图与输入。Chromium 体系主要参考 CDP；需要标准化跨浏览器交互时，可关注 WebDriver 和 BiDi。协议是基础设施，业务层仍要理解“哪个按钮代表发送”“哪个消息属于本轮”。依据：[CDP](https://chromedevtools.github.io/devtools-protocol/)、[Selenium BiDi](https://www.selenium.dev/documentation/webdriver/bidi/)。

**基于浏览器扩展的控制。** 在用户日常浏览器中接入页面，较自然地沿用该浏览器的登录环境，适合轻量分发和辅助侧栏。限制来自权限模型、扩展生命周期和各浏览器支持差异。当前插件属于这条路线；更广泛的控制也可通过浏览器扩展的调试接口实现。依据：[Chrome 扩展调试接口](https://developer.chrome.com/docs/extensions/reference/api/debugger)。

**基于截图的视觉操作。** 用截图判断按钮位置，再点击、输入和滚动，适合画布、图标按钮或缺少有效网页语义的界面。它受缩放、遮挡、滚动和视觉识别影响，通常应作为补充能力。依据：[Midscene](https://github.com/web-infra-dev/midscene)。

**网站主动提供结构化工具。** 如果网站愿意明确告诉代理“我提供哪些操作、需要哪些参数”，可减少对页面猜测的依赖。WebMCP 是值得跟踪的方向，但不能假定第三方 AI 官网已经支持。Chrome 官方于 2026 年 2 月公布早期预览；具体稳定支持范围应按目标浏览器版本核实。依据：[WebMCP 官方介绍](https://developer.chrome.com/blog/webmcp-epp)、[规范仓库](https://github.com/webmachinelearning/webmcp)。

## 六 开源项目对照与可复用能力

### 6.1 基础自动化工具

| 项目 | 适合解决的问题 | 本产品应借鉴什么 | 主要边界 |
| --- | --- | --- | --- |
| [Playwright](https://github.com/microsoft/playwright) | 确定步骤的网页交互与跨浏览器验证 | 语义定位、动作前自动等待、页面上下文、追踪记录 | 连接已有 Chromium 的 CDP 模式与原生连接能力不完全相同 |
| [Puppeteer](https://github.com/puppeteer/puppeteer) | Chrome 生态中的页面、网络与调试控制，也支持 Firefox | 已有浏览器连接、精细页面控制、浏览器事件 | 不是自然语言任务代理，需要自己组织业务流程 |
| [Selenium](https://www.selenium.dev/documentation/) | 标准化跨浏览器操作和企业测试部署 | WebDriver、BiDi、远程执行与 Grid 管理 | 对仅做桌面多 AI 工作台的产品，整套分布式体系可能过重 |

这三类基础工具比新一代浏览器代理框架更适合作为成熟度基准。成熟体现在长期演进、清楚的接口和测试生态，不代表对任意网站百分之百成功。

对于本项目，Playwright 的等待与追踪思路最值得借鉴：动作执行前检查目标能否交互，失败后保留足够信息判断是页面未准备好、元素改变还是业务拒绝。不要只通过固定等待若干秒来判断完成。依据：[自动等待](https://playwright.dev/docs/actionability)、[Trace Viewer](https://playwright.dev/docs/trace-viewer)。

如果把它连接到自研浏览器，必须验证真实输入、弹窗、跨域子页面、截图和下载。Playwright 官方明确指出，通过 CDP 连接的完整性低于其原生协议连接；“能接上”不能直接等同于“所有高级功能可用”。依据：[已有浏览器连接说明](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)。

### 6.2 面向 AI 助手的浏览器工具

| 项目 | 官方能力重点 | 具体借鉴点 | 本项目定位 |
| --- | --- | --- | --- |
| [Playwright MCP](https://github.com/microsoft/playwright-mcp) | 以结构化可访问性快照向模型提供页面信息，支持隔离环境、持久配置和扩展连接 | 页面快照、工具结果、接入已打开浏览器的交互 | 接入外部 AI 客户端的优先候选 |
| [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) | 浏览器交互、性能追踪、网络与控制台诊断 | 失败解释、网络观测、截图和开发调试 | 更适合研发诊断与复杂网页排障 |
| [agent-browser](https://github.com/vercel-labs/agent-browser) | 面向代理的浏览器命令工具，提供页面快照、元素引用、控制与会话能力 | 小而明确的操作词汇、结果格式、连接已有页面 | 与 ORCA 路线直接相关，适合轻量控制入口 |

从用户体验出发，“有 MCP”不应成为核心卖点。更有价值的承诺是：用户选择一个页面后，自己的 AI 助手可以在这一页面继续工作，过程可见，随时能暂停或接管。底层使用 MCP 还是本地工具接口，属于接入方式。

对于已有 Chrome 登录环境，应区分“通过扩展连接当前浏览器”和“另外启动一个浏览器配置”。Chrome 从 136 起限制对默认用户数据目录使用传统远程调试启动开关，不能把打开调试端口当成无条件接管用户日常 Chrome 的方案。依据：[Playwright MCP 扩展连接](https://github.com/microsoft/playwright-mcp#browser-extension)、[Chrome 官方变更说明](https://developer.chrome.com/blog/remote-debugging-port)。

### 6.3 自然语言代理与混合自动化

| 项目 | 能力重点 | 可以参考的产品机制 | 不应承诺的效果 |
| --- | --- | --- | --- |
| [Browser Use](https://github.com/browser-use/browser-use) | 把模型、浏览器和任务执行循环连接起来；可使用本地或远程浏览器 | 目标描述、过程观察、多步骤决策、自定义工具、最终结果 | 安装开源库后即可免费获得托管浏览器、模型推理和所有站点通行能力 |
| [Stagehand](https://github.com/browserbase/stagehand) | 将观察、动作和结构化提取结合，可与确定的网页操作混合使用 | 先识别目标、再执行确定动作，对难点局部使用 AI | 每一步都依赖模型也能获得固定成本和确定成功率 |
| [Skyvern](https://github.com/Skyvern-AI/skyvern) | 使用模型与视觉处理网站工作流，提供可视化流程构建能力 | 面向业务人员的流程、执行记录和结果验证 | 所有云服务附加能力都包含在开源仓库中 |
| [Midscene](https://github.com/web-infra-dev/midscene) | 通过视觉完成交互与断言，支持浏览器等界面 | 视觉兜底、动作截图、可读执行报告、检查用户实际看到的结果 | 看到了按钮就一定能正确执行复杂业务 |

对本项目的建议是采用混合执行：稳定站点的固定发送流程使用明确规则；网站变化时让 AI 辅助定位或诊断；只有用户提出更开放的任务时，才进入自主规划。这样可以控制延迟和模型成本，也更容易解释失败。

Browser Use 的开源执行库、模型调用与托管服务应分开核算。Skyvern 官方也明确区分开源核心与其托管服务中的部分反机器人能力。不能将商业服务宣传中的成功率直接当成本地开源部署的能力。依据：[Browser Use 费用与部署说明](https://github.com/browser-use/browser-use#faq)、[Skyvern 许可与服务边界](https://github.com/Skyvern-AI/skyvern#license)。

### 6.4 可直接参考交互的开源产品

| 项目 | 值得研究的界面与交互 | 对当前项目的启发 |
| --- | --- | --- |
| [Nanobrowser](https://github.com/nanobrowser/nanobrowser) | 浏览器侧栏、自然语言任务、实时状态、后续追问 | 如果继续做扩展，可以从统一输入扩展到可见的任务执行侧栏 |
| [Automa](https://github.com/AutomaApp/automa) | 用流程块连接浏览器自动化步骤 | 将高频重复任务保存为可复用流程，让用户理解“下一步会做什么” |
| [BrowserOS](https://github.com/browseros-ai/BrowserOS) | 浏览器内置代理；同仓库还提供面向代理工作的 BrowserOS neo | 区分用户日常浏览与代理任务页面，保留可观察的运行过程 |
| [ORCA](https://github.com/stablyai/orca) | 工作区内置页面、账号配置、页面选择、元素指认、代理控制 | 把浏览器变成任务工作台中的可共享操作对象 |

这些项目适合作为产品参考，不宜仅凭 GitHub 热度判断生产可靠性。例如，Nanobrowser 的“多模型”主要指给代理配置模型，不等于当前插件把同一问题发送到多个 AI 官网。BrowserOS 的浏览器分支路线，也与 ORCA 在桌面工作台内嵌网页的路线不同。

### 6.5 成熟度与许可应怎样纳入选型

建议按四个维度评估：目标网站是否适用、维护者是否持续维护、错误与恢复是否明确、部署与许可是否符合自己的产品形态。Star 数量只能说明关注度，不应作为成功率指标。

## 七 自研浏览器能否内置这些功能

### 7.1 可以内置 而且可以比扩展更自然

如果产品自己管理网页运行环境，就可以在创建页面时同时建立账号归属、任务归属、控制入口和状态记录。用户不必再理解扩展工作台、子框架和普通标签页之间的对应关系。

最直接的产品形态是：左侧放任务，中央放真实网页或回答对照，底部放统一提问，右侧按需显示任务进度。每个官网是应用管理的一个真实页面，既可以供用户手动操作，也可以交给代理控制。

原插件中最值得保留的是站点知识与业务流程，包括输入框定位、生成状态识别、回复采集、轮次归档和提示词组合。更可能替换的是扩展通信、框架绑定和通过修改响应头实现嵌入的部分。

### 7.2 不同技术路线对应不同产品目标

以下投入判断针对“已有网页前端开发经验、以多 AI 工作台为初始目标”的团队，不是通用成本结论。

| 路线 | 适用产品目标 | 有利条件 | 需要承担的工作 | 本项目判断 |
| --- | --- | --- | --- | --- |
| 继续做 Chrome 或 Edge 扩展 | 快速服务现有浏览器用户 | 复用日常浏览器和网站登录环境，分发较轻 | 扩展权限、官网嵌入、生命周期、浏览器差异 | 适合快速验证需求与保留轻量入口 |
| Electron 内置 Chromium 页面 | 多网页桌面工作台、与本地文件或任务深度结合 | 同一引擎、页面可控、与 ORCA 经验最接近 | 页面容器、账号、下载、弹窗、更新与资源管理 | 作为当前目标的优先概念验证路线 |
| CEF 嵌入 Chromium | 已有原生应用或需要较深原生整合 | 成熟嵌入框架，适合宿主程序控制 | 原生工程与界面、生命周期、平台维护 | 原生研发能力较强时适合 |
| WebView2 | 以 Windows 桌面为主要平台 | 与 Windows 生态整合，提供宿主与调试能力 | 跨平台扩展、运行时分发策略、界面与账号管理 | Windows 优先产品可认真评估 |
| Tauri 与系统 WebView | 重视应用体积、已有 Tauri 产品 | 复用系统 WebView，已有原生应用基础 | 不同系统引擎和控制能力不同，需要适配与验收 | 可以实现，但不应预设一套 CDP 控制逻辑跨三端通用 |
| Chromium 分支 | 希望做完整日常浏览器 | 对标签、扩展生态与浏览器行为控制更深入 | 内核升级、安全补丁、构建签名、安装更新、广泛兼容 | 只有完整浏览器战略明确时才优先考虑 |

基础依据：[Electron 页面容器](https://www.electronjs.org/docs/latest/api/web-contents-view)、[CEF](https://github.com/chromiumembedded/cef)、[WebView2 能力目录](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/overview-features-apis)、[Tauri 平台 WebView](https://v2.tauri.app/reference/webview-versions/)、[BrowserOS 的 Chromium 分支](https://github.com/browseros-ai/BrowserOS)。WebView2 是微软运行时与 SDK 路线，不能与开源 CEF 简单归为同一类开放源代码内核方案。

### 7.3 两个容易低估的迁移问题

**第一，Electron 使用 Chromium，并不代表可以直接安装运行所有 Chrome 扩展。** Electron 官方明确只支持部分扩展接口，并不追求与 Chrome 扩展系统完全兼容。当前插件依赖的后台生命周期、页面导航和请求规则等能力需要逐一迁移，不能把“把扩展放进去”当成已经验证的方案。依据：[Electron 扩展支持范围](https://www.electronjs.org/docs/latest/api/extensions)。

**第二，内置浏览器不是用户原来的 Chrome。** 用户在 Chrome 登录，不代表在新产品内自动登录。新产品需要清楚提供直接登录、账号配置切换，以及确有价值时的导入流程。会话数据可能存在设备绑定、存储差异和站点限制，不能承诺一键完整迁移所有账号。

### 7.4 建议内置的能力边界

| 能力 | 第一版需要达到的行为 | 后续可扩展方向 |
| --- | --- | --- |
| 页面管理 | 打开、关闭、定位、恢复明确的页面 | 页面分组、跨任务引用、休眠与恢复 |
| 账号管理 | 账号环境清晰可见，不同环境隔离 | 一个站点多个账号、任务专用账号 |
| 页面观察 | 文本结构、可交互控件、截图 | 局部更新、结构与视觉联合观察 |
| 页面动作 | 点击、填写、滚动、等待、导航 | 文件上传、下载、复杂编辑器和弹窗处理 |
| 任务控制 | 开始、暂停、停止、人工接管 | 多任务排队、断点恢复、可复用流程 |
| 回答管理 | 原文、来源、问题、状态一起保存 | 引用证据、结果比较、用户选择的综合整理 |
| 外部接入 | 统一内部控制接口 | 面向外部助手开放 MCP 或其他受控接口 |

无论选择哪种容器，都应该先定义这些产品能力，再选择底层工具。换容器不应导致用户的任务、历史和站点适配体系全部重做。

## 八 ORCA 内置浏览器源码分析

### 8.1 它的核心功能与当前插件不同

ORCA 把浏览器作为开发工作区的一部分。用户和开发代理可以在同一个页面里预览、检查、点击、填写、查看错误，再回到任务中继续工作。当前插件更专注于多家 AI 官网的协同提问和结果管理。

两者可以结合：ORCA 提供“页面怎样被管理和控制”的参考，当前插件提供“多个 AI 网站怎样共同完成一轮提问”的业务经验。

### 8.2 源码证实的主要控制链路

用产品语言描述，核心链路是：

**用户或代理提出操作 → 选定工作区和页面 → 页面命令进入队列 → 控制桥连接这个页面 → 浏览器执行 → 返回结果并更新页面状态。**

其中有七个值得复用的设计。

**一是页面有稳定身份。** ORCA 将内置页面与真实的浏览器内容对象登记起来，同时记录它属于哪个工作区、使用哪个账号环境。某个网页刷新或切换底层进程后，产品仍可以围绕同一个页面身份处理生命周期。桌面页面注册时还会校验对象是否为符合预期、已经应用策略的网页对象。

依据：[页面注册实现](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/browser-manager-registration.ts)。

**二是明确操作哪个页面。** 控制接口接受页面身份和工作区范围，不必依赖“屏幕上碰巧处于前台的是哪个标签”。测试中也覆盖了对指定页面获取快照而不切换当前活动页的行为。对多 AI 产品而言，这是防止问题发错站点、发错会话的基础。

依据：[页面目标选择](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-tabs.ts)、[页面路由测试](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-tab-routing.test.ts)。

**三是同一页面的操作进入同一队列。** 每个页面分别排队，执行时再次确认页面仍存在、绑定仍有效。其价值是避免多个操作同时修改同一个输入框，也为不同页面之间独立工作提供基础。它不能自动阻止用户鼠标与代理竞争，产品层仍应设计人工接管。

依据：[页面命令队列](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-queue.ts)。

**四是通过桥接复用 agent-browser。** ORCA 为内置页面建立本机 CDP 转接，把 agent-browser 的操作传给该页面的 Electron 调试通道。这样代理控制的是已在 ORCA 中打开的页面，而不是另行启动的、没有当前登录状态的空白浏览器。当前依赖清单与执行路径都能确认这一点。

依据：[项目依赖](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/package.json)、[控制执行](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-execution.ts)、[CDP 转接](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/cdp-ws-proxy.ts)、[Electron 调试通道](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/cdp-debugger-channel.ts)。

**五是用页面快照把网页转为代理可理解的操作对象。** 主要代理桥会将快照等请求交给 agent-browser；仓库还包含直接读取可访问性树、补充自定义交互元素、处理子框架和元素引用失效的实现。这里可借鉴的是观察后行动、页面变化后重新观察的闭环，不能理解为所有运行路径都经过同一个快照模块。

依据：[核心控制能力](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-core-commands.ts)、[快照构建](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/snapshot-engine.ts)、[元素引用恢复](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/cdp-ref-resolution.ts)。

**六是把账号配置作为独立对象。** ORCA 的浏览器配置对应独立存储分区，包含 Cookie、本地存储等会话环境，并有配置持久化与导入路径。工作区负责组织任务，账号配置负责身份；二者不应混为一谈。两个工作区如果选用相同账号环境，并不会因此自然变成两个独立账号。

依据：[账号环境管理](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/browser-session-registry.ts)、[配置文档](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/docs/site/content/docs/browser/profiles.mdx)。

**七是处理控制会话的结束与恢复。** 页面关闭、页面对象替换、辅助进程失效和连接超时都有相应清理逻辑。相关测试覆盖指定页面、页面切换、进程替换和会话重建。这说明真实难点不仅是点击操作，还包括浏览器长期运行后的状态一致性。

依据：[会话生命周期](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-lifecycle.ts)、[生命周期测试](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/agent-browser-bridge-session-lifecycle.test.ts)。

### 8.3 页面容器的事实与新产品的选择

当前研究版本中，ORCA 桌面浏览器使用 Electron 的 webview 页面；无界面的服务场景另有由主进程创建隐藏浏览器窗口的后端，两条路径统一登记为受管理的浏览器内容对象。它不是简单在普通网页里放几个 iframe。

源码中的浏览器后端抽象把差异集中在页面创建和销毁，控制层可以围绕统一页面对象工作。这种“页面如何显示”与“页面如何被控制”分开的设计，适合借鉴。

但不宜原样复制所有容器选择。Electron 官方当前对 webview 有明确的稳定性提示，建议考虑 WebContentsView 等替代方案。**新产品可以学习 ORCA 的控制架构，同时优先验证 WebContentsView 是否更适合自己的界面和生命周期。** 这是一项方案建议，不能写成 ORCA 已经采用 WebContentsView。

依据：[ORCA 浏览器后端](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/browser-backend.ts)、[隐藏页面后端](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/offscreen-browser-backend.ts)、[Electron webview 提示](https://www.electronjs.org/docs/latest/api/webview-tag)、[WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view)。

### 8.4 最值得产品经理学习的元素指认交互

ORCA 的 Design Mode 允许用户直接指认页面元素，把元素结构、样式与局部截图传给代理，减少“我说的是页面右边第二个按钮”这类语言歧义。具体信息是否包含源文件位置，取决于页面是否提供相应开发信息。

在多 AI 工作台中，可以把这一思路改造成三种更适合普通用户的交互：

- 选中某个回答区域，执行“把这段加入对比”。
- 指认输入区域，执行“以后对这个页面使用这里”，保存为经过验证的用户适配。
- 框选页面内容，再提出“解释这一部分”或“将这里整理成表格”。

后两者需要新增产品能力。自动生成的站点适配不能未经验证就永久替换原有规则；识别结果应让用户看到，并通过一次真实操作验证。

依据：[Design Mode](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/docs/site/content/docs/browser/design-mode.mdx)、[页面元素抓取](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/src/main/browser/browser-manager-grab.ts)。

### 8.5 ORCA 能让哪些部分更方便

| 工作 | 当前扩展需要处理的事情 | 参考 ORCA 后的改善 | 仍需要完成 |
| --- | --- | --- | --- |
| 展示多个官网 | 内嵌规则、子框架连接和标签页降级 | 宿主统一管理真实页面 | 多面板布局、内存与后台运行策略 |
| 控制正确页面 | 扩展面板与标签、子框架之间匹配 | 稳定页面身份与工作区范围 | 本地任务和官网会话的关系 |
| 代理操作 | 为每个动作建立扩展消息路径 | 统一控制接口与现成工具桥 | 各 AI 官网专用的发送语义 |
| 账号复用 | 沿用所在浏览器的账号环境 | 自有账号配置和明确隔离 | 新产品初次登录与导入兼容 |
| 错误解释 | 主要依靠页面状态和有限诊断 | 页面状态、截图、网络与控制台信息 | 翻译成普通用户能处理的错误 |
| 人工接管 | 在工作台与普通标签页之间切换 | 人和代理可操作同一内置页面 | 暂停、交还控制与防竞争机制 |
| 回复保存 | 插件已有较丰富的采集逻辑 | 获得更直接的页面和网络观测入口 | 完整回答判断、分支、分页和归档 |

所以答案是：**参考 ORCA 可以更方便地建设浏览器控制底座，尤其适合自研桌面工作台；多 AI 协同产品本身仍需要独立的业务层。**

### 8.6 ORCA 已经体现的兼容边界

ORCA 的账号文档对 Google 登录、导入限制和浏览器身份做了专门处理。它明确说明内置浏览器不等于完整 Chrome，Google 登录需要在 ORCA 内直接完成，部分操作系统保存的通行密钥仍不可用。这些边界值得直接纳入自研浏览器的验证计划。

另外，本地回环地址上的控制通道并不天然等于完整授权机制。若把浏览器控制开放给其他程序，仍需要限定可访问页面和动作，并给用户明确的停止入口。浏览器内核和 Electron 的隔离机制也不应为了方便自动化而整体关闭。依据：[ORCA 账号与兼容说明](https://github.com/stablyai/orca/blob/e3639ef8d69209b8278b41c0e722811960ea7ec0/docs/site/content/docs/browser/profiles.mdx)、[Electron 安全设计](https://www.electronjs.org/docs/latest/tutorial/security)。

## 九 更适合产品用户的交互设计

本节是建议方案，不表示当前插件或 ORCA 已经全部提供。

### 9.1 提供两个清楚的入口

**多 AI 对比**用于选择模型网站、统一提问、比较回答。默认行为固定、可预测，适合高频使用。

**网页助手**用于“在这个页面帮我完成一件事”。用户选择页面和任务范围后，代理再规划步骤、执行并回报。它可以逐步加入，无需在第一版就承担任意网站自动化。

不要让用户为了发送同一个问题给三家 AI，先理解“代理、工具、协议”等概念。产品界面只需要表达目标网站、当前账号、本次问题、执行状态和结果。

### 9.2 主界面建议

| 区域 | 主要内容 | 设计原因 |
| --- | --- | --- |
| 左侧任务列表 | 任务名、最近活动、未完成提示、置顶 | 工作围绕问题组织，不围绕浏览器标签堆积 |
| 顶部目标栏 | 官网、账号、当前会话、参与本轮的开关 | 发送前看清楚发给谁、使用哪个上下文 |
| 中央内容区 | 官网视图与统一回答视图切换 | 操作时保留官网，阅读时减少无关界面 |
| 底部统一输入 | 草稿、提示词模板、最终内容预览、发送目标数 | 让问题编辑和发送范围始终可见 |
| 可展开的进度区 | 各站状态、等待原因、失败恢复入口 | 用户不用猜“卡住了还是仍在生成” |

页面很多时不应强迫八列同时等宽显示。建议默认显示二到三个主要页面，其余页面以状态卡存在；用户可以随时聚焦某站，或者只看统一回答视图。后台页面是否继续运行，应与任务状态联动，而不是与是否可见简单绑定。

### 9.3 理想的发送与恢复流程

1. 用户输入问题，看到“将发送给 3 个站点”，并可展开查看最终组合内容。
2. 系统自动检查三个站点。某站未登录时，在该站旁显示“去登录”，其他站点保留准备状态。
3. 用户可以选择“处理后全部发送”，也可以明确改为“仅发送给已就绪站点”。默认保持当前产品的全部检查后发送，避免静默减少目标。
4. 正式提交后，分别显示已提交、生成中、已完成或状态未确认。
5. 某站失败时只恢复该站；已完成站点的结果继续保留。
6. 用户确认官网已经发送但本地没有收集到回答时，使用“重新采集”，而不是“重新发送”。

**应把“重新发送”和“重新采集”分成两个动作。** 这是该类产品非常重要的交互区别：前者可能消耗配额并产生新消息，后者只是获取现有结果。

### 9.4 给用户看的状态应准确表达事实

| 状态文字 | 用户应理解的事实 | 推荐下一步 |
| --- | --- | --- |
| 等待登录 | 当前网站还不能使用 | 在这个页面完成登录 |
| 需要人工验证 | 网站要求人工操作 | 暂停自动化，用户验证后继续 |
| 官网有未发送草稿 | 存在用户可能要保留的内容 | 查看并自行处理，或另开会话 |
| 已提交 | 网页已表现出接受消息的迹象 | 等待回答，不重复点击 |
| 提交状态待确认 | 无法证明网站是否已收到 | 打开官网核对后决定是否重试 |
| 生成中 | 网站仍在输出或执行 | 等待或由用户停止 |
| 回答已保存 | 当前回答已采集并通过适用检查 | 查看、比较、复制 |
| 内容可能不完整 | 有内容但不足以证明完整 | 显示原文入口与重新采集 |
| 本地保存失败 | 官网回答可能已经存在 | 保留页面，恢复保存，不重新提问 |

### 9.5 统一回答视图要支持比较与追问

第一版建议提供按轮次阅读、选中两到三个答案并排查看、复制某个答案、只向某家继续追问、打开对应官网消息。显示站点、问题、时间和采集状态，让用户始终知道答案来自哪里。

下一步可以支持把多家答案交给用户选定的一个 AI 做综合整理。但应该独立展示“各站原始回答”和“综合结论”，并说明这一步会把哪些内容发送给哪家服务。多家回答一致也不能直接视为事实已得到验证。

模型版本、联网状态、工具开关和上下文如果不能可靠获取，就显示“未确认”，不要由产品自行推测。否则比较结果可能被误解成严格的同条件模型评测。

### 9.6 人工与代理交接应留在同一页面

建议每个自动执行页面始终提供三个直接入口：暂停、我来操作、继续执行。用户接管后，代理停止新的页面修改；继续时重新观察当前页面，不沿用过期的位置和元素引用。

页面跳转、账号切换、用户编辑草稿都应视为会影响计划的状态变化。系统应先确认当前任务还适用，再继续下一步，而不是把之前排队的动作机械执行到底。

## 十 推荐的产品能力分层与迁移方式

### 10.1 六层功能结构

| 层次 | 面向产品的职责 | 优先参考 |
| --- | --- | --- |
| 工作台层 | 任务、面板、输入、历史、对比、人工接管 | 当前插件、ORCA |
| 任务执行层 | 目标选择、步骤、状态、并发、暂停和恢复 | 插件分阶段发送、ORCA 页面队列 |
| 站点适配层 | 识别登录、输入、发送、完成、会话与答案 | 当前插件的各站适配器 |
| 浏览器控制层 | 统一观察、定位、点击、填写、导航、截图 | agent-browser、Playwright、Puppeteer |
| 页面与身份层 | 网页生命周期、账号分区、任务归属 | ORCA、Electron 或 CEF |
| 数据层 | 原始问题、模板快照、原始回答、来源、版本和导出 | 当前插件的会话及采集快照模型 |

未来添加 AI 规划时，应让它调用已经定义好的浏览器动作和站点能力，而不是绕过它们另建一套失去状态记录的操作通道。

### 10.2 哪些部分可以复用 哪些部分应重新设计

| 当前插件资产 | 建议 |
| --- | --- |
| 各站输入与发送规则 | 迁移为与具体容器无关的站点知识，验证后复用 |
| 登录、忙碌、验证码识别 | 保留，同时将状态统一为用户可理解的语言 |
| 回答采集与完整性检查 | 重点保留，这是比基本点击更有价值的积累 |
| 提示词库、轮次记录与导出 | 保留产品语义，按新应用存储方式迁移 |
| iframe 嵌入策略 | 在独立内置页面方案中优先移除这项依赖 |
| 扩展后台与消息通道 | 替换为应用管理的控制路径，不假设可原封不动运行 |
| 短期发送去重 | 升级为持久的任务动作记录，明确待确认与已完成 |
| 官网地址恢复 | 增加账号身份与官网会话校验，避免只有地址没有上下文 |

网络采集应作为受控的站点适配能力，不宜升级为默认保存所有请求的通用网络监听器。页面控制更直接后，真正应该增强的是相关性校验和故障定位。

## 十一 分阶段实现与验证计划

### 11.1 先做有明确边界的概念验证

先选三类代表性站点：一个输入结构相对简单的站点、一个使用复杂富文本输入的站点、一个登录与页面防护较严格的站点。可以从 DeepSeek、Kimi、ChatGPT 或 Claude 中组合选择，最终按当前账号与目标用户场景确定。

在同一台目标机器上比较现有扩展与内置浏览器概念验证版本，验证以下闭环：首次登录、连续三轮发送、长回答采集、新建会话、应用重启后恢复、一个站点失败时保留其他结果。

通过这些验证以后，再扩展八个站点。先宣布支持八站、然后逐站补齐基础稳定性，会让产品问题难以归因。

### 11.2 功能阶段与退出标准

| 阶段 | 必须交付的用户能力 | 进入下一阶段的条件 |
| --- | --- | --- |
| 阶段一 多 AI 工作台 | 明确页面与账号、统一提问、逐站结果、原文保存、人工恢复 | 核心站点在真实登录条件下完成发送与采集闭环 |
| 阶段二 可靠性与迁移 | 持久任务记录、重新采集、异常恢复、历史迁移、适配诊断 | 页面刷新、应用重启、网络故障不造成静默串会话或重发 |
| 阶段三 受限网页助手 | 在指定页面执行有范围的任务、展示步骤、暂停与接管 | 可解释失败，并能确认任务结果而不仅是动作已执行 |
| 阶段四 可复用工作流 | 保存步骤、输入变量、执行记录、可选调度 | 高频流程有稳定成功率，维护成本可衡量 |
| 阶段五 更广泛的浏览器能力 | 多账号、多任务、外部助手接入、可选远程执行 | 身份隔离、并发资源和数据边界已可控 |

不建议在初版同时投入完整 Chromium 分支、任意网站代理、云端浏览器集群和复杂工作流市场。它们各自引入独立的产品与运维成本。

### 11.3 怎样定义成功

不能只统计“按钮点成功”。建议分别衡量：

- **发送确认率**：满足登录与就绪条件的目标中，有多少确认进入生成流程。
- **回答采集成功率**：网站已产生答案的目标中，有多少正确获取当前轮回答。
- **完整性正确率**：标为完整的回答中，有多少在人工抽查时确实完整。
- **会话关联正确率**：问题、账号、官网会话、本地任务与答案是否对应。
- **重复发送数量**：异常恢复是否引发重复消息。
- **人工介入率**：多少任务需要用户修复，介入后是否能继续。
- **恢复成功率**：刷新、断网或重启后，多少任务可以安全恢复。
- **使用成本**：发送前准备耗时、模型决策耗时、单任务模型费用、同时运行页面的资源占用。

还应分别统计单站成功率和全部站点完成率。作为说明性计算，如果八个站点的单站成功率均为 95%，并假设彼此独立，八站同时全部成功的概率约为 66.3%。这不是实测结果，只说明多目标系统必须认真设计部分成功和按站恢复。

### 11.4 建议的验收用例

| 场景 | 应满足的行为 |
| --- | --- |
| 三个站点中一个未登录 | 检查阶段不给其他站点提前发送；用户可明确调整目标 |
| 某站输入框已有草稿 | 不静默覆盖，允许查看或另开会话 |
| 一个站点仍在生成 | 明确提示等待或从本轮目标移除 |
| 点击发送后连接中断 | 标记待确认，不自动向全部站点重发 |
| 相同问题连续问两次 | 能将第二次新回答与第一次区分 |
| 回答包含标题、表格、代码和公式 | 保存正文与结构，不能只留下标题或状态文字 |
| 长对话分页或只渲染可见部分 | 完整性不足时明确提示，不把截断内容标成完整 |
| 官网存在多个回答分支 | 只采集当前选定分支对应的回答 |
| 用户在执行中切换页面 | 已绑定动作不误作用于另一个页面 |
| 用户修改了已暂存的问题 | 撤回操作不删除用户后来编辑的内容 |
| 官网完成但本地保存失败 | 可以恢复采集或保存，不重新消耗官网提问次数 |
| 两个任务使用不同账号配置 | 不发生账号环境混用 |
| 应用重启后恢复 | 能分辨待确认、已提交、已保存和需要人工处理 |
| 清理本地历史 | 不同时删除官网对话，除非用户另有明确动作 |
| 页面出现要求代理执行其他操作的文本 | 作为网页内容处理，不改变用户任务授权 |

可将“测试样本中误发、串账号、重复发送为零”设为发布门槛；这表示对规定样本的验收目标，不是对未来任意网站的绝对保证。成功率阈值应在概念验证后，按目标站点、账号等级和任务类型制定。

## 十二 长期维护与投入重点

### 12.1 真正持续发生的成本

| 成本来源 | 为什么会持续发生 | 产品应如何降低 |
| --- | --- | --- |
| 官网变化 | 输入框、按钮、会话接口和生成状态会变 | 站点适配独立维护，保留样例与回归用例 |
| 登录兼容 | 单点登录、通行密钥、验证码和设备绑定不断演变 | 同页人工登录、明确账号配置、对失败可解释 |
| 内容完整性 | 长文、附件、分页、分支与虚拟渲染各不相同 | 保留来源和证据，对未知状态明确展示 |
| 浏览器维护 | 内核更新、下载、证书、弹窗、存储和资源管理 | 尽量复用成熟容器与官方机制 |
| AI 推理 | 通用代理多一步判断就可能增加延迟与费用 | 固定流程用规则，复杂局部再调用模型 |
| 故障支持 | 用户只能描述“没有反应” | 提供本次任务的可读执行记录和故障位置 |

固定的多站发送本身不一定需要额外模型调用；如果启用自然语言代理或自动综合答案，才产生额外模型成本。用户原有官网订阅和使用额度也不会因为使用开源自动化工具而消失。

### 12.2 数据去向需要在产品中说清楚

至少区分三个位置：官网收到的提问和回答、工作台保存的本地历史、用于代理规划或答案综合的模型所接收的页面内容。浏览器在本地运行，并不代表页面内容绝不会被发送给外部模型。

产品可以默认本地保存历史，并让用户选择是否启用外部模型分析。发送密码、完整浏览器配置或无关页面内容不应成为普通任务的前提。代理也不应因为网页中的文字而自行扩大权限。

对于普通多站提问，用户点击一次明确的发送动作即可完成授权，不必每次填写都弹确认。涉及发布、付款、删除等外部后果时，应在最终动作前展示具体对象与内容，并允许用户决定是否执行。

### 12.3 本地与远程执行的取舍

本项目建议先以本地浏览器为主，用户可以直接登录、观察并接管，较符合多 AI 官网工作台的使用场景。

远程浏览器更适合长时间任务、统一运行环境或需要集中计算的场景，但会引入账号环境迁移、网络位置差异、文件传输、远程人工接管与资源调度。ORCA 的隐藏页面后端说明可将显示和控制分离，却不能证明远程环境与本地环境对所有网站等价。

是否使用远程服务器，应由实际任务决定，而不只是因为已有 Docker 服务器。当前需求调研不需要部署远程服务。

## 十三 功能到参考项目的最终映射

| 希望做出的功能 | 优先学习的位置或项目 | 推荐的交互结果 |
| --- | --- | --- |
| 同时向多个 AI 提问 | 当前插件的后台协调与站点策略 | 输入一次，明确选择目标，分站反馈 |
| 可靠获取本轮最终答案 | 当前插件的采集引擎、质量检查、消息关联 | 显示已保存、可能不完整、可重新采集 |
| 同一页面由人和代理接续操作 | ORCA 的页面注册、控制桥与生命周期 | 暂停后直接人工操作，再继续任务 |
| 同时运行多个独立页面 | ORCA 的页面队列和目标选择 | 每个任务绑定页面，避免抢占当前标签 |
| 多账号环境 | ORCA 的浏览器账号配置 | 页面明确显示当前身份，可选择独立环境 |
| 对外开放浏览器操作 | agent-browser、Playwright MCP | 选择允许控制的页面，再连接自己的助手 |
| 确定流程稳定运行 | Playwright、Puppeteer | 自动等待真实就绪，失败可定位 |
| 企业跨浏览器验证 | Selenium 与 Grid | 统一定义验证任务，在多环境执行 |
| 自然语言执行多步任务 | Browser Use | 任务目标、进行中的步骤、可中止与结果说明 |
| 在确定流程中局部使用 AI | Stagehand | 难点由 AI 识别，确定步骤按规则执行 |
| 视觉兜底与可见结果检查 | Midscene | 看图定位，保留动作截图与结果检查 |
| 非研发用户编排重复任务 | Automa、Skyvern | 可读流程、参数输入、步骤状态和失败恢复 |
| 完整浏览器内置代理 | BrowserOS | 浏览器级页面与身份管理，代理能力成为产品功能 |
| 用户直接指出想操作的区域 | ORCA 的 Design Mode 与元素抓取 | 点选页面元素后提问或加入任务 |
| 未来网站主动提供动作 | WebMCP | 支持时优先使用网站提供的明确能力 |

## 十四 立项前需要确定的产品选择

建议产品评审先形成以下选择，再让研发做详细技术方案：

1. **目标是多 AI 工作台，还是完整日常浏览器。** 当前需求更适合以前者起步。
2. **初始支持哪些站点。** 先验证代表性站点，再扩大到全部八站。
3. **账号如何组织。** 默认共享一个账号环境，还是允许每个任务选择不同账号环境。
4. **保存什么范围。** 当前轮答案、工作台会话、官网完整会话以及附件，必须分别定义。
5. **发送失败后怎样处理。** 优先保留成功结果，对不确定状态核对后恢复。
6. **是否引入额外模型。** 固定多站发送可以先不引入，自主网页任务和答案综合分别作为能力选择。
7. **是否需要外部助手接入。** 有需求时开放统一控制接口，避免与内部任务执行争抢页面。

对当前阶段，最值得验证的产品原型是：**参考 ORCA 的内置页面与控制架构，迁移当前插件的多 AI 业务能力，提供可观察、可接管、可恢复的协同提问工作台。** 用真实站点的登录、发送、采集和恢复结果决定后续投入，通用网页代理作为下一阶段扩展。
