## 一、目标与结论

在现有档案模块内，补齐个人档案、企业档案的**列表 / 卡片视图切换**，并让已经保存在 Markdown 中的备注、企业特别情况和自由正文真正参与档案搜索。

**推荐路线：一份档案文件作为事实来源，两种展示方式，共用查询与编辑能力；结构化基本信息继续放 YAML，长文本继续放 Markdown 正文，搜索通过可重建的内存索引提速。**

这是现有能力的增量增强，不是新建两套档案模块，也不是再次重构存储格式。保留当前独立实体 ID、任职 / 人际关系、资料目录和冲突保护。

## 二、原始需求与 email 的含义边界

原始建议包括：

1. 个人 / 企业基本信息录入后，可以切换列表和卡片。列表方便快速查看、横向对照；卡片适合概览。
2. 希望用「email」记录基本信息，把相关备注作为档案正文，并让后续搜索更方便。

这里不能未经确认就把 `email` 当作 `YAML` 的笔误，需区分：

| 概念 | 本方案的处理 |
| --- | --- |
| email = 邮箱地址 | 作为可选、多值的联系方式和检索字段，沿用现有 `emails: string[]`；不作为人物或企业的主键 |
| YAML / frontmatter = 笔记顶部属性 | 正是适合保存姓名、地区、邮箱、标签等基本信息的现有存储层，继续沿用 |
| email = 邮件正文 / 邮箱同步 / 从邮件建档 | 属于额外的数据来源集成，涉及授权、来源追踪、重复记录和敏感信息，本期不实现，也不假定这是用户已经授权的范围 |

本期采用与现有架构兼容、可逆的改进；若后续确认需要邮件来源导入，应另行定义需求，不用本 issue 顺带加入 OAuth、收发信或自动建档。

## 四、外部参考：GitHub 与 X

以下是可核验的相关样本，不是全平台热度排行；老议题会标注时间，避免把长期需求说成今天的新趋势。互动数量是本次读取快照。

### 4.1 同一份数据、多种展示：Obsidian Bases

[官方 Bases 文档](https://obsidian.md/help/bases)明确采用本地 Markdown 与属性作为数据来源，同一 base 可以有表格、列表、卡片等视图。由此借鉴**数据和布局解耦**，而不是要求 NAND 依赖或嵌入 Bases。

[官方 Properties 文档](https://obsidian.md/help/properties)将属性定位为小而独立的结构化信息，并明确属性中不渲染 Markdown、嵌套属性不由常规属性 UI 支持。由此建议姓名 / 邮箱 / 地区保留为扁平属性，长备注留在正文，不把履历和长文全部塞进深层 YAML。

### 4.2 GitHub：重复档案是长期真实需求，不能草率用邮箱代替身份

[Monica #1687：Merge contacts](https://github.com/monicahq/monica/issues/1687)创建于 2018-08-10，本次 API 读取为 30 次 reactions、14 条评论。其讨论既有将合并视作非紧急增强的意见，也有用户报告多来源导入后出现重复档案、活动不知道应记在哪个档案上的问题。

特别参考[导入后重复记录影响活动归属的用户评论](https://github.com/monicahq/monica/issues/1687#issuecomment-1336116760)。

对 NAND 的推论：邮箱和姓名适合用于发现疑似重复，但匹配到相同值不等于同一主体；一旦自动合并错误，还会影响履历、关系和附件归属。因此本期只保持身份稳定和搜索可见性，不加入自动合并。手动合并若以后实现，需有字段预览、关联迁移和恢复方案。

### 4.3 GitHub：多邮箱不是可省略的边缘情况

[Twenty #4985：Multiple phone numbers, links, and emails](https://github.com/twentyhq/twenty/issues/4985)创建于 2024-04-16，提出主邮箱与附加邮箱数组等结构，2024-07-15 关闭。本次读取为 1 次 reaction、4 条评论：它是**具体实现参考，不是高热度证据**。

对 NAND 的启发：保留已经实现的 `emails[]`，列表可显示首项加「+N」，详情可访问所有邮箱。首项只是展示顺序，本期不凭空引入必须迁移的 `primaryEmail` 新模式。

### 4.4 X：公开产品信号，谨慎使用热度结论

- [Obsidian 官方介绍 Bases 的公开帖，2025-05-21](https://x.com/obsdmd/status/1925211206186639403)：可核验搜索摘要为将一组笔记组织成数据库式视图。
- [Obsidian 官方 Bases 更新帖，2025-06-05](https://x.com/obsdmd/status/1930684621064384854)：可核验摘要提到公式能力、当前视图结果数量及表格长文本相关改进。

X 部分原帖访问返回 403 或空正文，本次无法可靠读取完整回复链和实时互动数量。因此这些仅作为相关公开设计信号，**不声称是当前热门榜，也不声称 X 社区证明了 YAML 或邮箱能提高搜索速度**；多视图和存储的技术依据另由官方文档核对。

综合取舍：借鉴多视图、结构化属性和可读正文；不照搬大型 CRM 的同步系统、不引入 AI 写作、不用热度替代性能测试。

## 五、交互方案：一个档案入口，两种布局

### 5.1 入口与默认行为

只在当前档案页面工具栏增加「列表 / 卡片」分段切换，不增加 Ribbon 按钮、工作台一级菜单或常驻状态栏项目。个人与企业仍在现有档案模块内切换。后续统一工作台接入时复用同一个档案内容面板，不新造第二套导航。

建议初次打开个人档案默认列表、企业默认卡片；两类各自记住用户选择。对旧工作区恢复数据缺少显示模式的情况，按旧卡片模式回退；显式偏好始终优先。旧状态与新页面的默认规则必须有测试，不能靠字段缺失产生随机体验。

### 5.2 列表展示

桌面采用可扫描的紧凑行 / 表格形式；窄面板以名称 + 两行辅助信息呈现，不能单纯把所有列挤到不可读。

| 档案类型 | 建议默认可见字段 | 需注意 |
| --- | --- | --- |
| 个人 | 姓名、现任企业 / 职务、地区、邮箱摘要、标签 | 允许同时在多家企业任职，不擅自选出唯一主雇主；多个邮箱用首项 +N，完整值可在详情访问 |
| 企业 | 企业名称、地区、网站、已收录在职联系人数量、标签 | 人数来自已有成员关系，明确是「已收录」数量，不宣称是企业实际员工总数 |

修改时间可作为次级信息或后续可选列。首期不引入复杂的列配置器、批量编辑和拖拽表格。姓名 / 名称是主要进入详情的操作；复制邮箱等辅助操作不得误触进入详情。键盘用户应能独立访问这些操作，不把交互按钮嵌入另一个整行按钮。

### 5.3 卡片展示

复用现有视觉语言与头像首字占位。信息顺序建议为「名称 → 当前企业 / 核心信息 → 地区 / 联系方式 → 标签」。统一卡片密度与留白，长文本省略后可以在详情查看；无需头像也不能留下大面积空白。

搜索有正文命中时，列表和卡片都展示一条短摘要及「命中：备注 / 企业特别情况 / 正文」等来源，不把全文塞进卡片。

### 5.4 切换必须是纯展示行为

两种布局共用同一个查询结果、筛选条件、排序、分页、详情和编辑入口。切换不得清空关键词、筛选、当前页或选中的实体，不得触发档案重写或全库重新扫描。

由于列表和卡片行高不同，分别保存浏览位置或使用首个可见记录作为锚点，不直接在两种布局间套用相同像素滚动值。搜索或筛选变化仍按原逻辑回到首屏，结果减少时校正越界页码。

空库、无匹配、加载中、读取部分失败、重复 ID、禁用模块等状态需两种布局一致。切换控件提供文字 / tooltip、可见焦点和可读选中状态；手机不能只靠 hover 完成操作。

## 六、记录方式：保留现有文件协议

继续使用：

```text
档案/
  个人档案/
    示例联系人/
      基本信息.md
      沟通记录.md
      附件.pdf
  企业档案/
    示例企业/
      基本信息.md
  档案格式说明.md
```

属性和正文分工：

- YAML：`nand-type`、`nand-id`、`name`、`aliases`、`emails`、`region`、`tags` 等现有基本字段。
- 正文托管区域：现有履历 / 关系表格，以及 `traits`、`habits`、`notes`。
- 正文非托管区域：用户自行添加的 Markdown，保留原位置和内容；参与搜索不等于被插件接管编辑。
- 相关资料：继续以实体目录归属，不复制进属性，也不改为插件私有数据库。

以下仅展示现有协议的简化示意，不是替换全部区域的迁移模板：

```markdown
---
nand-type: person
nand-id: 62422a25-15d6-4458-9b9b-4cc40d9c9378
name: 示例联系人
emails:
  - contact@example.com
region: 杭州
tags:
  - 合作伙伴
---

# 示例联系人

## 备注

<!-- nand:notes -->
沟通时偏好先看书面方案。下次讨论供应链合作。
<!-- /nand:notes -->

## 用户自行补充

可以直接写普通 Markdown，搜索应能够找到这些文字。
```

邮箱允许为空、允许多个、允许修改；两份档案可以记录同一公共邮箱，但仍是两个独立实体。搜索规范化不改原值；不能全局删除邮箱的 `+` 后缀或点号来自动合并联系人。

复用 `parseRecord` / `patchMarkdown` 的原有保护：编辑基本属性不能覆盖正文，修改备注不能重写不相关正文；同字段 / 同区域并发冲突仍提示，而不是最后一次保存静默覆盖。重复 ID、无效 YAML、损坏边界和引用冲突不能被这次增强绕过。

## 七、搜索方案：范围、证据、成本分别处理

### 7.1 本期搜索范围

默认搜索「档案信息」，即该实体 `基本信息.md` 的可读信息；另保留「仅基本信息」选项。界面明确说明未包含其他附件内容。

必须涵盖：

- 已有姓名、别名、邮箱、电话、地区、标签等基本字段。
- 已有任职企业名称与职务，并补齐部门、任职备注等可读信息。
- 性格、习惯、个人备注、企业特别情况。
- 关系说明 / 关系备注和所关联实体的可读名称。
- `基本信息.md` 内用户自行追加的自由正文。

正文提取排除 YAML 分隔块、插件内部 HTML 标记、UUID 等实现信息；保留用户可读的正文文本、链接显示文字等。不要直接对整份 `raw` 做 `includes()`，否则会出现技术标记误命中、同一内容重复和难以定位来源的问题。不能为抽取纯文本而执行笔记中的脚本、Dataview 查询或远程嵌入。

### 7.2 查询语义与命中说明

保持中文子串可用，英文检索可忽略大小写；多关键词可以按 AND 组合，但应在界面和测试中明确语义，不能静默改变旧关键词的含义。保留现有筛选「组内 OR、组间 AND」。输入法组词完成后再提交最终查询，避免中文输入期间反复重置焦点 / 内容。

结果返回对应档案、命中字段 / 正文区域和短摘要；摘要仅用安全文本与受控高亮，不能注入原始 HTML。点击命中应进入相应档案并展开对应托管区域；自由正文命中提供打开原始笔记及可用的定位提示，不假装当前详情已渲染所有非托管内容。

保留「名称 / 最近修改」排序语义，不能因为加入全文检索就暗中按相关度重排。相关度排序可作为后续显式选项；需要时再定义邮箱精确匹配、名称、关联名称、正文之间的权重。

### 7.3 派生索引，而非另一份主数据

在现有 `ContactsIndex` 上增加按文件路径维护的搜索文档，结构可包含：记录身份、规范化基本字段、分区纯文本、来源信息、内容版本。名称仅用于展示，重复 ID 的异常记录也不能因错误地只用 ID 作缓存键而被覆盖消失。

在 `set / remove / clear` 和档案变更链路更新 / 移除缓存；每次用户输入只查询内存，不重新读取磁盘或重新序列化文件。尽量复用 `ArchiveRecord.raw` 和解析结果，避免无必要地长期持有多份完整正文。

必须覆盖依赖失效：企业改名后，相关人物的任职公司名称搜索要更新；被关联人物改名后，关系名称搜索同样要更新。文件重命名、删除、目录切换、重复 ID 恢复和重新读取也要同步处理。先收集受影响关联，再更新缓存，避免移除旧关系后丢失需要失效的对象。

首期采用预计算文本 + 现有内存筛选，并记录性能数据。不预设 SQLite、向量库、远程检索或 Worker 是必要前提。只有测量证明规模需要时，再引入倒排索引 / 后台工作线程。异步路径必须有版本 / 目录代次校验，旧查询和旧目录结果不能覆盖当前页面。

### 7.4 相关资料全文检索作为后续独立范围

实体目录内其他 `.md` 的正文全文检索，可后续按需开启：结果按档案归组，并附命中文件及段落来源。PDF、图片 OCR、Office 附件解析另行评估；本期只保持原有相关资料文件名 / 路径搜索，不宣称附件全文已覆盖。

## 十、验收标准

- [ ] 个人与企业均可切换列表 / 卡片；同一查询下结果集合、顺序和总数一致。
- [ ] 切换不丢关键词、筛选、页码和实体选择；详情返回能恢复合理浏览位置。
- [ ] 两种模式、两类档案的偏好恢复正确；旧状态缺字段 / 非法值不会报错或随机切换。
- [ ] 在个人备注、企业特别情况、任职 / 关系备注及非托管正文写入仅在那里出现的测试词，均可搜索命中并看出来源。
- [ ] 同一个邮箱的两份不同档案不会自动合并；无邮箱和多邮箱档案仍可正常创建、浏览和搜索。
- [ ] 企业改名后人物搜索可使用新公司名；若旧公司名仅来自已失效的派生名称，不能继续幽灵命中。
- [ ] 原始笔记外部修改、文件 / 文件夹改名、删除、切换资料根目录、重新读取后结果正确；过期异步结果不能回写。
- [ ] 插件身份 / 编辑边界标记不成为普通全文命中噪声；正文提取不执行脚本或远程请求，摘要无 HTML 注入。
- [ ] 只修改基本属性，原正文及非托管内容保持不受影响；同区域并发冲突、无效格式和重复 ID 保护仍有效。
- [ ] 不改现有档案目录及主键，不自动迁移旧平铺文件，不新增第二份权威数据存储；保留旧资料。
- [ ] 空状态、部分读取失败、错误态、手机 / 窄面板、弹出窗口、深浅色和中英文布局均通过回归；键盘与输入法可用。
- [ ] 测试报告明确本期全文范围只含入口档案笔记，不包含相关附件内容。

### 性能验收方法（待测目标）

使用 100 / 1,000 / 5,000 条混合档案，正文长度分别覆盖空、约 2 KB、约 20 KB，并加入长中文备注和多任职关系。记录硬件、Obsidian 版本、档案数量、正文总量、冷启动、热查询 P50 / P95、渲染时间与内存增量。

建议基准目标：在约定桌面基线、1,000 条档案且每条约 2 KB 正文时，热查询核心耗时 P95 ≤ 100 ms（含筛选 / 排序，不含输入防抖）；当前 60 条分页的显示切换 P95 ≤ 100 ms。5,000 条及长正文为压力测试，报告实际结果并据此决定进一步优化，不能拿小数据目标替代大规模测试。

结构性要求：热查询和布局切换不读取档案磁盘文件、不重建全库；单文件内容变化更新对应搜索文档及受影响的关联文档。移动端单列报告，不能直接宣称达到桌面指标。

## 十一、明确不做

本期不做 AI 辅助写作、向量 / 语义检索、自动上传档案、邮箱授权与同步、邮件自动建档、自动实体合并、PDF / 图片 OCR、复杂 CRM 流水线或存储格式整体迁移。所有性能改善以测量为准，不能宣传「换成 YAML / email 就自然更快」。
