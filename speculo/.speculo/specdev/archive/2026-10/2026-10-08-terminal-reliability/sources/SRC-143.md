## 现状 / Current behavior
终端 helper `nand-pty` 由 Obsidian **渲染进程**直接启动（`src/modules/agent/platform/desktop/pty/helper.ts:56` 的 `spawn(binary, [], { stdio: ['pipe','pipe','pipe'] })`）。

实测 `nand-pty` 进程除了 stdin、stdout、stderr 外，还持有**48 个从渲染进程继承来的、与终端无关的文件句柄**，其中只有 3 个带 `FD_CLOEXEC`。按类型分：

| 数量 | 类型（路径已泛化） |
|---|---|
| 16 | Chromium 共享内存段（`/tmp/.org.chromium.Chromium.*`，已 unlink，显示 `(deleted)`；因为测试时用了 `--disable-dev-shm-usage`，平时一般在 `/dev/shm`） |
| 11 | socket（含 stdio 的 3 个；抽查 11 个中 **8 个与渲染进程共用同一 inode**，即 Chromium 的 IPC / mojo 通道） |
| 7 | Obsidian 应用包内的只读文件（`app.asar`、`resources.pak`、`icudtl.dat`、`v8_context_snapshot.bin` 等） |
| 7 / 4 | `anon_inode:eventpoll` / `anon_inode:eventfd` |
| 2 | `/proc/<渲染进程 pid>/status`、`/proc/<渲染进程 pid>/statm` |
| 1 | 字体文件 |
| 3 | `/dev/ptmx`（helper 自己打开的，正常） |

**`nand-pty` 启动的 shell 没有继承这些句柄**：bash 只有 `0/1/2/255 → /dev/pts/N` 四个（`portable_pty` 在子进程里关闭了多余 fd），所以终端里运行的命令和智能体拿不到它们。问题只在 helper 这一层。

## 复现 / 检查方法
1. Linux 桌面，打开工作台 → AI Agent → 新建终端（或命令「NAND: 新建终端」）
2. 在系统终端执行：
   ```sh
   P=$(pgrep -f 'binaries/nand-pty')
   ps -o ppid=,args= -p "$(ps -o ppid= -p $P)" | grep -o -- '--type=renderer'   # 父进程是渲染进程
   ls -l /proc/$P/fd | wc -l                                                     # 约 51
   ls -l /proc/$P/fd | awk 'NR>1{print $NF}' | sort | uniq -c | sort -rn          # 类型分布
   for f in /proc/$P/fdinfo/*; do awk '/^flags/{print $2}' "$f"; done            # 第 3 位八进制 2 = O_CLOEXEC，绝大多数没有
   for c in $(pgrep -P $P); do ls -l /proc/$c/fd; done                           # shell：只有 pts
   ```

## 影响 / Impact（客观评估）
- **不是可直接利用的漏洞**：`nand-pty` 是插件自带、经过 sha256 校验的程序；它不监听端口，也没有把这些句柄传给 shell。
- 它是**纵深防御**问题：
  - helper 一旦出现缺陷（例如解析帧时的内存安全问题），或者以后改为启动其他子进程时漏掉关闭 fd，它手里就有渲染进程的 IPC 通道和共享内存可用。
  - 这些继承来的引用会让对应的共享内存和 socket 一直活着，直到 helper 退出（helper 会在 Ctrl+Q / SIGTERM / SIGKILL 后正常退出，实测无孤儿进程，所以只是生命周期偏长）。

## 建议 / Proposal
建议在 helper 一侧处理，因为 Node 的 `spawn` 无法控制继承哪些非 stdio fd：
- `nand-pty` 在 `main` 入口、进入事件循环前关闭 fd ≥ 3。Linux 5.9+ 可用 `close_range(3, ~0U, 0)`；更早的内核或其他 Unix 可遍历 `/proc/self/fd`（或 `/dev/fd`）逐个关闭，或至少设上 `FD_CLOEXEC`。macOS 可用 `/dev/fd` 遍历。
- 加一条集成测试：启动 helper 后检查 `/proc/<pid>/fd` 中 ≥ 3 的条目只剩 helper 自己创建的（epoll、eventfd、ptmx）。
- （可选）Windows 侧确认 `CreateProcess` 的 `bInheritHandles` 和句柄白名单情况。

## 验收标准 / Acceptance criteria
- [ ] Linux 下 `nand-pty` 启动后，`/proc/<pid>/fd` 里没有 `/tmp/.org.chromium.*`、`/dev/shm/*`、Obsidian 应用包文件、`/proc/<渲染进程>/…`，也没有与渲染进程共用 inode 的 socket
- [ ] shell 子进程仍只有 pts（保持现状）
- [ ] 终端功能、重启 / 退出行为不变
