# TDD 红绿规则

适用于需要新增行为证据的缺陷修复和新能力。先检查现有测试能否证明验收；纯文档、无行为变化和低影响可逆修改使用适用检查，不为满足格式新增测试或强制变异。高风险路径仍需足以证明风险受控的行为验证。

1. 从 Ready Ticket/Spec 选择下一条最小可观察行为，并写下已确认 seam。
2. 只为该行为编写一个会因目标能力缺失而失败的测试或验证。
3. 运行并观察红灯；失败原因必须是目标行为缺失，而不是语法、夹具或环境错误。
4. 只写使当前测试通过的最小生产代码，不预测后续切片。
5. 运行定向测试并观察绿灯，记录命令与结果。
6. 进入下一条窄垂直切片；周期性运行受影响回归。

保持行为的重构使用既有回归证据；为目标行为必要的局部结构调整可在当前切片完成，仍受范围和不变量约束，不顺手扩大重构。

## 完成门

- 需要红绿循环的切片有对应 red/green 证据；复用已有测试或不适用时记录验证依据；
- 一个循环只有一个 seam、一个测试和一个最小实现；
- 测试没有通过删除、跳过、吞错或放宽断言制造绿色；
- 未以“顺手重构”扩大任务范围。

## 强制变异验证

使用强制变异时，先保存基线 hash/diff，修改后核对实际执行文件的 diff 与测试选择。只有预期行为断言 red 才有效；编译错误、错测或变异未落地均不计。恢复原内容、复跑基线并核对 diff，把全过程记入 Evidence。诊断协议见 <Path>{roots.workflows}/specdev/D-diagnose-bugs/D-diagnose-bugs.md</Path>。
